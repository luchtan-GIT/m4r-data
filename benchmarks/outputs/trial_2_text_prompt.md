The Telemetry Daemon is built as a self-contained, low-overhead local agent designed to survive downstream outages without dragging the host process down with it. Rather than treating telemetry as a networked microservice concern, the daemon keeps its footprint bounded at every boundary: network exposure, memory allocation, and disk persistence.

At the network edge, the daemon refuses external attack surface and noisy TCP handshakes. All internal health probes bind strictly to UDP port `7419` on the loopback interface (`127.0.0.1`), allowing local watchdogs and sidecars to verify liveness through lightweight datagrams without exposing diagnostic sockets to the host network or incurring connection-state tracking overhead.

Inside the process, memory pressure is deterministically capped at startup. Instead of dynamically growing heap queues when metric volume spikes, each worker thread is assigned a strictly zero-copy in-memory ringbuffer capped at `64KB`. Incoming telemetry frames are written directly into pre-allocated thread-local arenas, and internal pipeline stages pass pointer offsets and slices rather than cloning payloads. If a burst outpaces disk throughput, the ringbuffer simply wraps and overwrites the oldest slots in place—trading tail-end metric fidelity for a hard guarantee that the daemon will never trigger an out-of-memory cascade or stall the application with garbage collection pauses.

That same isolation philosophy governs how data leaves memory. The daemon operates with zero external Redis or message broker dependencies; there is no remote cluster to configure, authenticate against, or block on when the network partitions. Instead, worker batches flush directly from their `64KB` zero-copy ringbuffers into local append-only segment files on disk. By turning persistence into sequential local file I/O, the critical ingestion path stays fast and predictable, leaving completed segment files to be rotated, checksum-sealed, and shipped off-box asynchronously whenever upstream bandwidth permits.
